# Agent Note: 跨进程会话单写入者持久化

Status: implemented

[English](2026-08-19-session-single-writer-durability.md) | 中文

## 问题

会话写入过去只在单个 `PersistenceCoordinator` 内部串行化。第二个 Host 可以在原 Host 仍存活时加载并修复一个未闭合会话，随后已被取代的 Host 又可能从陈旧游标追加迟到的工具结果。JSONL 使用追加模式，但没有写入者所有权或版本比较并交换；SQLite 事务也无法区分不同 Host 代际。后续加载会把由此产生的重复序号分支正确拒绝为已提交区域中的序号缺口，但持久化层此前已经接受了相互冲突的写入。

## 决策

`PersistenceBackend` 强制要求实现 `acquireWriter` 和 `releaseWriter`，并要求每次追加或修复都接收 `WriteExpectation`，其中包含租约、协调器已观察到的版本以及下一个逻辑序号。成功的变更会返回带有新版本的 `WriteCommit`。`PersistenceCoordinator` 延迟到首次写入时获取所有权，只在提交成功后推进游标和版本，在会话退役后释放租约，并在关闭后端前等待所有写入链和租约释放完成。

JSONL 后端把不透明令牌存入 `session.writer` 边车文件。租约接管、追加、修复和按令牌匹配的释放都使用同一个跨进程写入锁，因此所有权检查和日志变更不会与另一个 Host 的接管交错。JSONL 版本使用设备号、inode 和字节大小，而不使用 Windows 时间戳；后者的延迟落定行为不适合作为写入路径中的比较并交换标识。

SQLite 后端把所有权存入 `writer_leases`。租约检查、版本检查、逻辑尾部检查、事件变更、版本递增和返回新版本都在同一个 `BEGIN IMMEDIATE` 事务内完成。模式版本 18 增加租约表；打开完全符合预期的版本 17 模式时，会在模式事务内原地迁移到版本 18，而任何已被改动的版本 17 模式仍会因所有权校验失败而被拒绝。

严格序号校验保持不变。共享后端测试覆盖第二个 Host 修复未闭合会话，以及接管后迟到工具结果到达的场景。后端测试覆盖 JSONL 锁与版本行为、SQLite 事务式接管和模式迁移，以及关闭后端前等待租约释放完成的拆卸流程。

## 备选方案

**只修复受影响的会话日志。** 不予采用，因为仍在运行的旧 Host 可能再次追加；每次持久化变更都必须强制校验写入者所有权。

**依赖桌面端单实例锁。** 不予采用，因为孤立的 Host 可能比 GUI 进程存活更久，而 Web Host 和测试 Host 也不共享 Electron 生命周期。

**加载时按序号去重事件。** 不予采用，因为序号相同的两个分支并不等价，静默选择其中一个会削弱损坏检测。

**使用时间戳版本并等待其稳定。** 不予采用，因为这会增加延迟，而且无法把 Windows 时间戳发布变成原子的比较并交换标识。

**把新的后端方法设为可选。** 不予采用，因为缺少租约和版本强制校验的后端会静默恢复原来的损坏路径。

## 影响

令牌已被取代的活动 Host 现在会明确抛出 `SessionWriterSupersededError`；基于已变化持久版本的写入会抛出 `SessionRevisionChangedError`。JSONL 会为每个会话创建写入者边车文件，并在每次变更时创建短生命周期的锁文件。如果进程在持锁期间终止，锁辅助函数不会根据文件年龄猜测所有权，因此孤立锁仍需运维人员明确移除。SQLite 数据库会在首次打开时从模式 17 迁移到 18，并保留现有会话行和事件。派生投影仍按版本键控，并会在修复提交后重建。
